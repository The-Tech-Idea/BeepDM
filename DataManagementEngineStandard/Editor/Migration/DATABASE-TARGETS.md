# Database target migration lifecycle

MigrationManager.BindDatabaseTarget(provider, claimPath, legacyClaimBinding) binds the optional IDatabaseTargetMigrationProvider before a datasource can open. Catalog creation and entity/schema migration are separate steps owned by the same framework: prepare the native target, open its datasource, then use normal MigrationManager entity/schema operations. Applications supply no SQL and keep business CRUD through UnitOfWork.

DatabaseTargetMigration captures immutable provider/server/catalog/ownership-scope identity. It saves and reads back durable creation intent before native dispatch under a private exclusive file lease, then verifies the native owner. Never retry, drop or adopt an unknown target automatically. A missing catalog with a saved dispatched intent, an existing catalog without the matching owner or a mismatched/corrupt claim requires explicit reconciliation. Preserve the claim and database. A pre-cancelled operation changes nothing; cancellation after acknowledged creation settles owner status before reporting cancellation.

Exists is read-only and does not connect without an existing valid claim. PrepareAsync(createIfMissing:false, allowExistingUnowned:false) cannot create. Explicit configured main-database reuse can permit an existing target without claiming/stamping it; demo or other owned targets must not opt into that policy. A native failure is propagated, not interpreted as a missing target.

New v2 claims bind provider/scope as well as server/catalog/owner. Legacy unscoped v1 claims are refused by default. An application that already owns that exact old protocol must explicitly provide DatabaseTargetLegacyClaimBinding for the declared provider/scope. Reads preserve old bytes; the framework contains no application-specific names. Native ownership still must match. No legacy compatibility flag grants authorization to adopt arbitrary databases.

Providers implement only immutable identity, existence observation, owner observation, native creation and owner stamping. The SQL Server LocalDB provider uses its configured driver factory, validated user-catalog identifiers, parameterized metadata, bounded connection/command timeouts and no caller-supplied statement. Other providers are not implicitly supported. Framework native/provider contracts and fictional LocalDB lifecycle checks do not certify production performance, arbitrary providers, Unix file semantics or whole-product release compliance.
